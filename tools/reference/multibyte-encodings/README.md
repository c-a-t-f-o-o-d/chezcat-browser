# Pinned Chinese, Japanese and Korean encoding data

This directory retains normative labels, two-byte indexes and four-byte range
starts for ChezCat's original GBK, gb18030, Big5, EUC-JP, ISO-2022-JP,
Shift_JIS and EUC-KR decoders. It contains no browser engine implementation or
third-party decoder code.

## Source and provenance

The source is the [WHATWG Encoding Standard repository](https://github.com/whatwg/encoding)
at commit [`7d2e3e08e11f57ba1b080390b490d53648c6f69c`](https://github.com/whatwg/encoding/tree/7d2e3e08e11f57ba1b080390b490d53648c6f69c).
The eight retained upstream files are exact copies at that revision:
`encodings.json`, `LICENSE`, `index-gb18030.txt`, `index-gb18030-ranges.txt`, and
`index-euc-kr.txt`, plus `index-big5.txt`, `index-jis0208.txt`, and
`index-jis0212.txt`. During acquisition, their Git blob identifiers and byte
lengths were checked against the pinned commit's Git tree. The raw index files
are not converted through an operating-system or language-library codec.

[`manifest.json`](manifest.json) records the repository, revision, source paths,
byte lengths, Git blob SHA-1 identifiers, and SHA-256 hashes. The offline
generator checks these identities before using any input. Updating the data
requires an explicit revision/manifest change, review and regeneration. This
is the same upstream revision as the foundation's single-byte encoding data.

## Selection and representation

The generated label lookup includes exactly seven canonical names and 38 labels:
GBK has nine labels, gb18030 one, Big5 five, EUC-JP three, ISO-2022-JP two,
Shift_JIS eight, and EUC-KR ten. Labels for other encodings remain in the
unmodified JSON but are not generated here. The caller normalizes ASCII case
and surrounding ASCII whitespace before lookup.

| Index | Mapped pointers | Generated pointer domain |
| --- | ---: | ---: |
| GB18030 two-byte index, shared by GBK and gb18030 | 23,940 | 0–23,939 |
| EUC-KR two-byte index | 17,048 | 0–23,939 |
| Big5 index | 18,590 | 0–19,781 |
| JIS0208 index, shared by the Japanese decoders | 7,724 | 0–11,279 |
| JIS0212 index, used by EUC-JP | 6,067 | 0–8,835 |
| GB18030 four-byte range starts | 207 | Normative pointer/code point pairs |

GB18030, EUC-KR and both JIS tables use fixed `u16` arrays and preserve omitted
pointers as `0xffff`. Their mapped values are validated as BMP scalars distinct
from that sentinel. Big5 uses a `u32` array because 1,713 mapped values lie above
the BMP. Its hole sentinel is `0x110000`, outside Unicode's scalar domain; valid
supplementary characters remain exact.

The array domains follow their byte/pointer representations: 126 × 190 for the
Chinese simplified and Korean indexes, 126 × 157 for Big5, 60 × 188 for the full
Shift_JIS JIS0208 pointer space, and 94 × 94 for JIS0212. The JIS0208 domain
includes extensions above the 94 × 94 plane used by EUC-JP and ISO-2022-JP.
Their decoder algorithms select the applicable pointers. No table fills holes
or substitutes operating-system codepage mappings. Checked runtime lookup
returns `None` for holes and pointers outside the table; the decoder owns error
handling and input restoration.

The four Big5 pointers that produce pairs of code points (1133, 1135, 1164 and
1166) remain absent from the raw index and generated table. Those special pairs
and the Shift_JIS private-use pointer range are algorithmic decoder rules,
not extra mappings inserted by the generator.

The range array retains the exact ordered pointer/code point starts, including
the supplementary-plane start `(189000, 0x10000)`. Four-byte arithmetic, the
reserved pointer interval, the upper Unicode boundary, and the standard's
exceptional mapping belong to the original decoder, not this data generator.
The tables alone do not establish correct decoding behavior.

Index descriptions may include literal Unicode control characters. Source rows
are split only at LF, so those characters cannot create spurious rows.

## Reproduce and check

From the repository root, using Python 3 and its standard library:

```console
python tools/generate_multibyte_encodings.py
python tools/generate_multibyte_encodings.py --check
python tools/check_multibyte_encodings.py
```

Generation is deterministic and offline. `--check` compares the generated bytes
with `src/text_encoding_multibyte_data.rs` without rewriting that file. Controls
exercise input corruption, invalid provenance, missing or repeated inputs,
paths outside the selection, each index's own pointer domain, BMP/supplementary
values and holes, range ordering, invalid scalars, and exact selected labels.
They also require the retained
`LICENSE` and `notices/WHATWG-Encoding-LICENSE.txt` to have identical bytes.

Separate Rust decoder tests read these retained raw files independently of the
generator when checking runtime behavior. Browser integration, streaming/fatal
semantics, and API exposure require their own evidence. Only generated data and
original Rust code enter the runtime; Python and the raw files add no production
dependency or browser-startup network activity.

## Scope

This directory supplies normative data for F02's Chinese, Japanese and Korean
decoders. Encoding output, replacement decoding where required, document
encoding selection, HTML prescan and parser restart behavior, XML encoding
policy, and full browser WPT coverage remain separate requirements. Retaining
all labels in the upstream JSON does not advertise support for other encodings.
