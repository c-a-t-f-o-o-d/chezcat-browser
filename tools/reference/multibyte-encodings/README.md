# Pinned GBK, gb18030 and EUC-KR data

This directory retains normative labels, two-byte indexes and four-byte range
starts for ChezCat's original GBK, gb18030 and EUC-KR decoders. It contains no
browser engine implementation or third-party decoder code.

## Source and provenance

The source is the [WHATWG Encoding Standard repository](https://github.com/whatwg/encoding)
at commit [`7d2e3e08e11f57ba1b080390b490d53648c6f69c`](https://github.com/whatwg/encoding/tree/7d2e3e08e11f57ba1b080390b490d53648c6f69c).
The five retained upstream files are exact copies at that revision:
`encodings.json`, `LICENSE`, `index-gb18030.txt`, `index-gb18030-ranges.txt`, and
`index-euc-kr.txt`. During acquisition, their Git blob identifiers and byte
lengths were checked against the pinned commit's Git tree.

[`manifest.json`](manifest.json) records the repository, revision, source paths,
byte lengths, Git blob SHA-1 identifiers, and SHA-256 hashes. The offline
generator checks these identities before using any input. Updating the data
requires an explicit revision/manifest change, review and regeneration. This
is the same upstream revision as the foundation's single-byte encoding data.

## Selection and representation

The generated label lookup includes exactly three canonical names and 20 labels:
GBK has nine labels, gb18030 has one, and EUC-KR has ten. Labels for other
encodings remain in the unmodified JSON but are not generated here. The caller
normalizes ASCII case and surrounding ASCII whitespace before lookup.

| Index | Mapped pointers | Generated pointer domain |
| --- | ---: | ---: |
| GB18030 two-byte index, shared by GBK and gb18030 | 23,940 | 0–23,939 |
| EUC-KR two-byte index | 17,048 | 0–23,939 |
| GB18030 four-byte range starts | 207 | Normative pointer/code point pairs |

The two-byte tables use fixed `u16` arrays and preserve all omitted pointers as
`0xffff`. The generator verifies that each mapped value is a valid BMP scalar
distinct from that sentinel. It does not fill holes, substitute operating-system
codepage tables, or confuse the legacy GB2312 and Windows-949 labels with other
algorithms. Checked runtime lookup returns `None` for holes and pointers outside
the table; the decoder owns error handling and input restoration.

The range array retains the exact ordered pointer/code point starts, including
the supplementary-plane start `(189000, 0x10000)`. Four-byte arithmetic, the
reserved pointer interval, the upper Unicode boundary, and the standard's
exceptional mapping belong to the original decoder, not this data generator.
The tables alone do not establish correct decoding behavior.

Index descriptions may include literal Unicode control characters. Source rows
are split only at LF, so those characters cannot create spurious rows.

## Reproduce and check

From the repository root, using Python 3 and its standard library:

```console
python tools/generate_multibyte_encodings.py
python tools/generate_multibyte_encodings.py --check
python tools/check_multibyte_encodings.py
```

Generation is deterministic and offline. `--check` compares the generated bytes
with `src/text_encoding_multibyte_data.rs` without rewriting that file. Controls
exercise input corruption, invalid provenance, missing or repeated inputs,
paths outside the selection, index holes and boundary values, range ordering,
invalid scalars, and exact selected labels. They also require the retained
`LICENSE` and `notices/WHATWG-Encoding-LICENSE.txt` to have identical bytes.

Separate Rust decoder tests read these retained raw files independently of the
generator when checking runtime behavior. Browser integration, streaming/fatal
semantics, and API exposure require their own evidence. Only generated data and
original Rust code enter the runtime; Python and the raw files add no production
dependency or browser-startup network activity.

## Scope

This increment supplies the GBK, gb18030 and EUC-KR portion of F02. Other
multibyte families, encoding output, document encoding selection, HTML prescan
and parser restart behavior, XML encoding policy, and full browser WPT coverage
remain separate requirements. Retaining all labels in the upstream JSON does
not advertise support for those other encodings.
